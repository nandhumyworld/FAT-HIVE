🏗️ High-Level Design Generation

Claude can translate a system description into a structured architecture — services, data flows, component responsibilities — as readable text you can refine into diagrams.

❌ "Design a URL shortener"
✅ "Design a URL shortener handling 10K writes/sec and 500K reads/sec. Users are global. Shortened links must resolve in under 100ms. Include: component diagram, data flow, key trade-offs, and one alternative architecture with its pros/cons."
Full HLD Prompt
You are a senior solutions architect. Design the high-level architecture for:

System: [Name and one-sentence purpose]
Scale: [Requests/sec, data volume, users]
Latency SLA: [e.g. <200ms p99 for reads]
Constraints: [Cloud provider, existing stack, budget limits]

Produce:
1. Component Diagram (as labelled ASCII or text boxes)
2. Data Flow — happy path step by step
3. Key design decisions and why (not just what)
4. Top 3 failure modes and mitigations
5. Alternative architecture with trade-offs vs your recommendation

Be opinionated. State assumptions clearly.

Force a structured comparison before you commit to an approach.

Trade-off Analysis
I'm choosing between these architectures for [system]:

Option A: [e.g. Monolith with read replicas]
Option B: [e.g. Microservices with event sourcing]
Option C: [e.g. Modular monolith with async workers]

My context:
- Team size: [N engineers]
- Current scale: [X req/sec], expected in 18 months: [Y req/sec]
- Deployment target: [Cloud/on-prem]
- Biggest constraint: [latency / cost / team expertise]

Compare on: Operational complexity, scalability ceiling, team fit, migration risk.
Give a weighted recommendation. Be direct.
Component Breakdown
Break down this system into components:

System: [Your system description]

For each component:
- Name and single responsibility
- What it consumes (inputs)
- What it produces (outputs/events)
- Technology choices with reasoning
- SLA it must meet
- Who owns it (team or service)

Format as a structured list. Then draw the dependency graph in ASCII.
🏗️ Exercise 1 — Generate a Real System's HLD

Pick a system you've built or are designing now

  • Run the Full HLD prompt with your actual scale numbers and constraints
  • Ask Claude: "What would break first if traffic grew 10×?"
  • Request an alternative architecture and compare the trade-offs
  • Note: which failure modes did you not think of yourself?

📐 Low-Level Design Support

LLD is where architecture becomes code. Claude can generate class diagrams, DB schemas, API contracts, and interface definitions — all as structured, editable text.

DB Schema Generation
Design the database schema for: [system / feature]

Requirements:
- [Key entities and their relationships]
- [Query patterns: e.g. "users query orders by date range"]
- [Scale: rows per table at 1 year, 5 years]
- [DB engine: PostgreSQL / MySQL / MongoDB]

For each table/collection:
- Fields with types, constraints, and nullable rules
- Primary keys, foreign keys, and indexes
- Reasoning for index choices
- Any denormalisation decisions and why

Then: write the CREATE TABLE SQL (or schema doc for NoSQL).
Flag any N+1 query risks in the schema.
Class / Domain Model
Generate the class/domain model for: [feature or service]

Context: [Language — Java/Python/TypeScript, framework if relevant]

Include:
- All domain entities with attributes and types
- Methods with signatures (no implementation needed)
- Relationships: inheritance, composition, aggregation
- Design patterns applied and why (e.g. Strategy, Repository, Factory)

Output as:
1. UML class diagram in text/PlantUML notation
2. Key design decisions explained
3. Interface definitions for dependency injection points
Service / API Contract
Define the API contract for: [service name]

Consumer: [Who calls this service and why]
Provider: [This service's responsibilities]

Generate:
1. OpenAPI 3.0 spec (YAML) for all endpoints
2. Request/response schemas with validation rules
3. Error codes and their meanings
4. Authentication and rate limit headers
5. Idempotency requirements for write operations
6. Versioning strategy recommendation

Flag: any breaking change risks vs [existing API version if applicable].
📐 Exercise 2 — LLD for a Current Feature

Take any feature you're building or have built

  • Generate the DB schema — compare Claude's index choices to yours
  • Ask: "What queries will be slow at 10M rows and how would you fix them?"
  • Generate the API contract and check it against your actual implementation
  • Spot any inconsistencies or gaps between the two

🔍 Scalability & Edge Case Identification

AI-guided review surfaces what experienced engineers forget to check — because they're inside the system. Claude approaches it from the outside.

🧪 Scalability Review Framework
1
Identify Hotspots

Which components receive disproportionate load? Where is shared state?

2
Stress the Assumptions

What happens at 10×, 100× traffic? Where does the first thing break?

3
Map Edge Cases

Empty state, concurrent writes, retry storms, partial failures, clock skew.

4
Evaluate Mitigations

For each risk: rate likelihood × impact, then recommend the minimum viable fix.

Scalability & Edge Case Review Prompt
Review this system design for scalability and edge cases:

[Paste your design / architecture description]

Current load: [X req/sec]   Peak load: [Y req/sec]
SLA: [Latency and availability targets]

Analyse:
1. Top 5 bottlenecks at 10× current load — with specific components named
2. Edge cases I haven't handled (concurrent writes, retry amplification, partial failure, etc.)
3. Single points of failure that aren't obvious
4. Data consistency risks in distributed paths
5. For each issue: severity (P1/P2/P3), likelihood, and minimum viable mitigation

Be critical. Don't summarise — identify real problems.
⚠️
The Edge Case Checklist

Always ask Claude to check: empty collections, concurrent writes to the same row, clock skew between services, retry storms on failures, cascade deletes, and token/session expiry mid-request.

🧠 Design Review Using Claude

A good design review is structured and challenging — not just confirmatory. Claude can play devil's advocate, identify gaps, and produce a written critique you can share with your team.

Devil's Advocate Review
You are a senior principal engineer reviewing this design.
Your job is to be constructively critical — not destructive, not confirmatory.

Design: [Paste your design]

Challenge it on:
1. Assumptions that seem reasonable but will hurt us at scale
2. Choices where simpler alternatives exist that we overlooked
3. Operational complexity that isn't justified by the requirements
4. Security or compliance risks baked into the architecture
5. What the team will regret in 12 months

For each: explain the risk, its impact, and a concrete alternative.
Conclude with: "The most critical change before we ship this is..."
Structured Design Critique
Produce a structured design review for the following:

[Paste design doc / architecture description]

Format:
## Strengths (what's done well and why it matters)
## Risks (concrete problems, not vague concerns)
## Gaps (requirements not addressed in the design)
## Improvement Recommendations (prioritised P1/P2/P3)
## Open Questions (decisions that need explicit resolution)

Be specific. Reference named components. No generic best-practice advice — only issues specific to this design.
Design Review Checklist Generator
Generate a tailored design review checklist for this system:

[System description]
Domain: [e.g. payments, auth, data pipeline, ML inference]
Team size: [N]   Deployment: [cloud/on-prem/hybrid]

Produce a 20-point checklist covering:
- Functional completeness
- Non-functional requirements (latency, availability, consistency)
- Security and access control
- Observability (metrics, logs, traces, alerts)
- Operational runbooks and failure recovery
- Data migration and backwards compatibility

For each item: what to check and what a passing answer looks like.

Use a design doc you've written or reviewed recently

  • Compare Claude's critique to what your team raised in the real review
  • Generate the tailored checklist — use it in your next actual review
  • Note: what did Claude catch that your team didn't?

🔌 MCP — Deep Dive

The Model Context Protocol (MCP) is an open standard that lets Claude communicate with external tools, data sources, and services — turning Claude from a chat interface into an agent with real-world reach.

How MCP Works

🖥️ MCP Server — what it does ▼

An MCP Server is a lightweight process that exposes capabilities to Claude. It declares three things:

Tools — callable functions Claude can invoke (e.g. read_file, run_query, create_pr).

Resources — data Claude can read (e.g. a file, a database row, a Slack channel's history).

Prompts — reusable prompt templates the server makes available to the host.

Servers communicate via JSON-RPC 2.0, over stdio (for local processes) or SSE/HTTP (for remote servers). They can be written in any language — official SDKs exist for TypeScript, Python, and Kotlin.

💻 MCP Client (Host) — what Claude does ▼

The host (Claude Desktop, Claude Code, or your custom app) manages the connection to one or more MCP servers. When Claude wants to use a tool, it:

1. Sends a tools/call request to the relevant MCP server.

2. Receives the result and incorporates it into its reasoning.

3. Can chain multiple tool calls across multiple servers in a single turn.

Claude never directly accesses the external service — it goes through the MCP server, which enforces permissions and handles auth.

🔐 Authentication & Security in MCP ▼

MCP servers handle authentication on behalf of Claude. Common patterns:

Environment variables — API keys and tokens are passed to the MCP server process at startup, not exposed to Claude directly.

OAuth 2.0 — for hosted services (GitHub, Slack), the server handles the OAuth flow and token refresh.

mTLS — for enterprise deployments, mutual TLS between client and server.

Claude only sees tool results — it never sees raw credentials. Permission scopes are defined in the server, not in Claude's prompt.

With the GitHub MCP server, Claude can read repos, list PRs, create issues, and post comments — directly from your conversation.

GitHub MCP — PR Review Prompt
List the open pull requests in [owner/repo] that have been open more than 3 days.

For each PR:
- Summary of what the PR does (from title and diff)
- Files changed and lines added/removed
- Any blocking review comments
- Your assessment: ready to merge, needs changes, or needs discussion

Then: rank them by review urgency and tell me which to look at first.

The Postgres MCP server lets Claude query your database, explain query plans, and suggest schema improvements — without you writing a single SQL line.

Postgres MCP — Schema & Query Analysis
Connect to the database and:

1. List all tables with row counts and last-updated timestamps
2. Find tables with no indexes other than the primary key
3. Identify foreign keys that are missing an index on the child side
4. Show the 5 slowest queries from pg_stat_statements (if available)

Then recommend the top 3 index additions, estimated impact, and the exact CREATE INDEX statements.

Slack MCP enables Claude to read channel history, post summaries, and create structured updates — useful for automated incident reports and sprint summaries.

Slack MCP — Incident Summary
Read the last 4 hours of messages from #incidents.

Summarise:
1. Active incidents — name, severity, current status, assigned owner
2. Resolved incidents — timeline of what happened and fix applied
3. Any action items mentioned that haven't been assigned yet

Post the summary as a formatted message to #engineering-digest with the current timestamp.

The file system MCP gives Claude read/write access to your local files — enabling code review, refactoring, and documentation generation without copy-pasting.

File System MCP — Codebase Review
Read all Python files in ./src/ recursively.

Analyse and report:
1. Functions longer than 50 lines — name, file, length
2. Functions with no docstrings
3. Duplicate logic patterns across files (don't list trivial ones)
4. Import cycles if any
5. Any obvious anti-patterns (God classes, magic numbers, bare excepts)

Output a prioritised list of refactoring targets with file:line references.
💡
Setup Tip: Claude Desktop Config

MCP servers are configured in claude_desktop_config.json. Add each server under "mcpServers" with its command, args, and env. Claude Desktop auto-discovers and connects on startup.

🔗 Building Simple MCP Workflows

Multi-tool chaining is where MCP becomes powerful. Claude can read from one tool, reason, and write to another — all within a single conversation turn.

Example: PR Triage → Slack Update Pipeline

📥 Read PRs
GitHub MCP
→
🧠 Claude Analysis
Prioritise & summarise
→
💬 Post to Slack
Slack MCP
→
📋 Log to File
File System MCP
Multi-Tool Chaining Prompt
Do the following in sequence using your available tools:

Step 1 — GitHub: List all open PRs in [owner/repo] modified in the last 24 hours.
Step 2 — Analyse each PR: classify as (needs-review / blocked / ready-to-merge).
Step 3 — GitHub: Add a label "needs-review" to any PR with no reviewer assigned.
Step 4 — Slack: Post a structured daily PR digest to #engineering:
  - Ready to merge: [list]
  - Blocked (waiting for CI / author response): [list]
  - Needs reviewer: [list + @mentions for relevant team members]
Step 5 — File system: Append a timestamped summary to ./logs/pr_digest.log

Confirm completion of each step before proceeding to the next.
🔧
Design Pattern: Step-Confirm-Continue

For multi-tool workflows, always ask Claude to confirm each step before proceeding. This lets you catch tool errors early and maintain a clear audit trail of what was changed.

🔗 Exercise 5 — Build Your Own Workflow

Design a 3-step multi-tool workflow for your team

  • Identify a repetitive manual task your team does weekly (standup prep, release notes, etc.)
  • Map it as: Source Tool → Claude Analysis → Target Tool
  • Write the chaining prompt using the step-by-step format above
  • Run it and review — what did Claude get right? What needed correction?

🤖 Claude Code + MCP & Practical Patterns

Claude Code is a command-line agent that can execute code, run tests, and manage files autonomously. Combined with MCP, it gains access to external context — making it a genuinely autonomous engineering agent.

Claude Code reads your codebase, runs commands, and fixes issues — MCP gives it live data from your issue tracker, DB, and monitoring tools to close the loop.

Claude Code + MCP: Bug Triage Agent
# In Claude Code (claude command line)

claude --mcp github --mcp sentry "
Do the following autonomously:

1. Fetch the top 5 unresolved Sentry errors from the last 48 hours
2. For each error: find the relevant source file in ./src using the stack trace
3. Read the code around the error location
4. Diagnose the root cause — explain it in one paragraph
5. Propose a fix with the exact code change
6. Create a GitHub issue with: error summary, root cause, proposed fix, and affected file:line
7. Output a summary table: Error | Root Cause | Issue URL

Do not apply any fixes without my confirmation."
Automated Code Review Pipeline
Review the diff in this pull request:

[Paste diff or use GitHub MCP to fetch it]

Review against these standards:
1. Security: injection risks, auth gaps, exposed secrets
2. Performance: N+1 queries, missing indexes, blocking calls
3. Correctness: logic errors, off-by-one, null handling
4. Testability: can this be unit tested? Are there hidden dependencies?
5. Style: naming clarity, unnecessary complexity, missing docs

Format each finding as:
- Severity: P1 / P2 / P3
- File:Line
- Issue description
- Suggested fix (code snippet where applicable)

End with: overall recommendation — Approve / Request Changes / Needs Discussion.
PR Summarisation for Stakeholders
Summarise this pull request for two audiences:

PR: [Title, link, or paste diff]

Audience 1 — Engineering (technical):
- What changed and why
- Files affected and key logic changes
- Test coverage added
- Deployment considerations (migrations, feature flags, config changes)

Audience 2 — Product / Non-technical:
- What this enables for users (plain English)
- Any behaviour changes they'll notice
- Risk level and rollback plan

Keep each summary under 150 words. No jargon in the product summary.
Test Generation at Scale
Generate comprehensive tests for this function/class:

[Paste code]

Language/Framework: [e.g. Python/pytest, Java/JUnit, TypeScript/Jest]

Generate:
1. Happy path tests — all standard inputs and expected outputs
2. Edge cases — empty, null, max/min values, boundary conditions
3. Error cases — invalid input, external service failures, timeouts
4. Concurrency tests if applicable (race conditions, thread safety)
5. Performance test (if the function has a complexity concern)

For each test:
- Descriptive name (test_[scenario]_[expected_outcome] format)
- Setup, action, assertion (Arrange-Act-Assert)
- Comment explaining what risk this test covers

Then: identify the 3 most important tests if we can only add 3 right now.
